COMMENT 1:

explicitly show that the 17.48x speedup was achieved by the Event-Driven 
baseline engine on the Cislunar profile, whereas the proposed Adaptive 
engine achieved only a 9.02x speedup. Claiming the performance metric of 
a baseline method as the achievement of the proposed method is a critical 
error in scientific reporting. The abstract and conclusion must be corrected 
to accurately reflect the 9.02x peak speedup of the adaptive method."

RESPONSE:
We thank the reviewer for catching this reporting error. We have thoroughly 
corrected all occurrences across the manuscript. In our updated benchmark 
suite:
- The peak speedup achieved by our proposed Adaptive engine is 9.68x on the 
  Cislunar profile (achieving a 12.3x reduction in integration steps), 7.00x 
  on the Elliptical profile, and 5.18x on Mars.
- The ~17.4x speedup is now explicitly and solely attributed to the 
  Event-Driven baseline.
- Furthermore, we now explicitly explain why Event-Driven's 17.4x speedup 
  comes at an unacceptably severe accuracy penalty: freezing physics updates 
  during communication blackouts causes over 7,200 km of trajectory drift, 
  whereas Adaptive matches continuous ground-truth physical accuracy.

CHANGES MADE:
- Abstract, Highlights, Table 3, Section 4.3, Figure 6(b) caption, and 
  Conclusion have been corrected to state the exact speedups (9.68x Cislunar,

COMMENT 3:
"The results in Table 3 indicate that the Adaptive engine is actually 
slower than the Fixed-Step baseline for the Mars profile, recording a 
speedup factor of 0.77x (wall time of 0.1744s vs 0.1342s). While Section 5.4 
briefly attributes this to the overhead of 'frequent step contractions and 
ODE solver restarts near the ingress and egress boundaries', a high-tier 
journal requires a more rigorous analysis of this limitation. The authors 
should expand on the boundary conditions and event densities under which 
their adaptive orchestrator becomes a computational bottleneck."

RESPONSE:
We thank the reviewer for this critical observation. We analyzed the Mars 
trace and found the root cause: the previous heuristic contracted step sizes 
near occultation boundaries but lacked a boundary-intercept guard, causing 
repeated step overshoots and high-frequency chattering.

To solve this, we implemented a predictive boundary event guard in the engine 
(simulation/engine.py):
    dt = min(dt_proposed, t_next_event - t)

The step size proactively contracts to land exactly on the event boundary, 
eliminating overshoot. Quiescent blackout and coasting arcs then expand 
cleanly up to 3600 s and 600 s. 

RESULTS:
- Adaptive steps on Mars dropped from 486 steps to just 52 steps.
- Mars execution time dropped to 0.0263 s, turning the former 0.77x slowdown 
  into a 5.18x speedup over Fixed-Step (0.1360 s), with zero boundary chatter 
  and 0.0 ms event detection error.

CHANGES MADE:
- Implemented the predictive boundary event guard rule in simulation/engine.py 
  and documented it in Section 3.4 (Equation 20).
- Updated Table 3 with the new Mars metrics (52 steps, 5.18x speedup).
- Added an analytical bottleneck analysis in Section 4.3.2 deriving the 
  mathematical step-count relationship between event density and solver overhead.

COMMENT 4:
"In Section 4.3, the authors verify their discrete engine's logical correctness 
by comparing the simulation output against a numerical integration using a 
'very fine reference step size' (\Delta t_{ref} = 0.01s). The authors should 
clarify if this validation holds true under extreme network load conditions 
(e.g., massive packet flooding during a brief line-of-sight window), and how 
the adaptive engine prevents missing micro-events that might occur between 
the 1.0-second DT_MIN lower bound."

RESPONSE:
We have clarified both the extreme network load validation and sub-second 
micro-event handling in Section 3.4 and Section 4.3:
1. Discrete Network Independence: Network packet arrivals and queue drain 
   events are processed through discrete queue operations. Under packet flooding, 
   the queue tracks discrete drops and custody releases without altering the 
   macro physical step.
2. Micro-Event Interception: The event-guard rule enforces that if a scheduled 
   network event or line-of-sight transition occurs before the proposed step 
   dt, the orchestrator contracts dt to match the exact remaining time to that 
   event. This guarantees that no micro-events are skipped between macro steps.

CHANGES MADE:
- Added text in Section 3.4 explaining how the predictive event guard contracts 
  to intercept micro-events exactly at their event epochs.
- Added validation discussion in Section 4.3 confirming zero drop discrepancy 
  against the fine-step reference (dt = 0.01 s) under line-of-sight packet bursts.

COMMENT 5:
"Equation 11 calculates dynamic channel capacity using a modified continuous 
Shannon limit approximation. However, real-world deep space links rely on 
discrete Variable Coding and Modulation (VCM) schemes defined by specific 
CCSDS standards (e.g., LDPC or Turbo codes). Treating capacity as a continuous 
logarithmic curve may artificially smooth out the discrete step-changes in 
throughput that occur when a physical radio switches modulation schemes. The 
authors should either implement a realistic, step-based ModCod threshold model 
or rigorously justify why the continuous Shannon fluid approximation is 
sufficient for a study focused on high-fidelity discrete-event synchronization."

RESPONSE:
We agree with the reviewer. While continuous Shannon capacity provides a 
theoretical upper envelope, real deep space transceivers switch modulation 
and coding schemes at discrete SNR thresholds. We have implemented a discrete 
CCSDS ModCod staircase model mapped to hardware SNR thresholds.

CHANGES MADE:
- Added Equation 8 in Section 3.2 formulating the discrete ModCod mapping table 
  (QPSK, 8PSK, 16APSK, 32APSK with LDPC codes) compliant with CCSDS 131.2-B-1 
  and CCSDS 231.0-B-1.
- Retained the continuous Shannon curve strictly as an analytical upper bound.
- Added discussion explaining how discrete ModCod transitions reinforce the 
  need for adaptive stepping, as fixed steps miss switching boundaries.

COMMENT 7:
"Equation (13) models DTN buffer occupancy as a continuous fluid flow based 
on bitrates. However, the DTN Bundle Protocol (RFC 5050/9171) referenced by 
the authors operates on discrete bundles, not continuous data flows. A fluid 
approximation masks actual discrete queueing dynamics, such as bundle 
fragmentation, discrete custody transfer acknowledgments, and packet 
boundaries, which are critical to protocol accuracy. The authors need to 
clarify if their DiscreteEngine actually processes discrete network packets 
or merely integrates flow rates. If it is a fluid model, claims regarding 
high-fidelity protocol simulation should be significantly tempered."

RESPONSE:
We agree with the reviewer. We have replaced the fluid model with a discrete 
packet queue summation and clarified the scope of our network model.

In the updated engine, buffer occupancy is tracked by summing discrete queued 
packets with explicit 1024-byte MTU boundaries, integer byte allocations, and 
discrete custody transfer events. We also clarified that the engine models 
temporal queue occupancy and custody handover timing for co-simulation 
synchronization, rather than acting as a full-stack RFC 5050/9171 network emulator.

CHANGES MADE:
- Reformulated buffer occupancy as a discrete summation over queued packets 
  (Equation 9) in Section 3.3.
- Added scope clarification in Section 3.3 regarding queue abstraction versus 
  full-stack protocol emulation.
- Retained the continuous fluid equation strictly as an analytical reference 
  baseline in Section 4.3 for verification.
